# Как внести вклад в Toudocu

[English](CONTRIBUTING.md)

Делайте изменения небольшими, подтверждёнными и удобными для проверки. Toudocu —
строгий TypeScript CLI и React-приложение, работающие на Node.js 24+.

## Перед изменением

- Прочитайте [STD-TS-001](docs/quality/STD-TS-001.md): там находятся правила
  TypeScript-кода и обычный цикл проверки.
- Если меняются поведение, контракт, документация или портал, прочитайте
  [STD-DOCS-001](docs/quality/STD-DOCS-001.md).
- Сначала найдите существующую архитектурную границу, модуль, контракт и
  рабочую задачу. Не добавляйте новую абстракцию, если нужная уже есть.
- Держите независимую от фреймворков семантику в `packages/core`, I/O — в
  `packages/platform-node`, HTTP — в `packages/server`, UI — в `apps/web`.

## Рабочий процесс

1. Создайте небольшую ветку с одной понятной целью.
2. Измените реализацию и минимальный набор связанных тестов.
3. Обновите исходную документацию, если изменились наблюдаемое поведение,
   команда, API, настройка или пользовательский путь.
4. Выполните проверки, которые требует применимый стандарт.
5. В pull request опишите результат, важные ограничения и выполненные команды.

## Основные команды

```bash
pnpm format
pnpm lint
pnpm typecheck
pnpm test
pnpm test:browser
pnpm build
pnpm check
```

Для полного цикла используйте `pnpm check`. Для изменений интерфейса дополнительно
запускайте `pnpm test:browser`. Релизные команды нужны только тогда, когда задача
затрагивает артефакты поставки.

## Правила документации

- Канонические русские исходники находятся в `docs/`. Каталог
  `docs-en/` обновляется только явным процессом английского перевода.
- Портал всегда строится из Markdown; не исправляйте сгенерированный результат
  вручную.
- Прямо отмечайте отсутствующее и ещё не реализованное поведение.
- Не создавайте runbook без реальной эксплуатационной процедуры.
- Успешная проверка структуры не заменяет смысловую вычитку.

## Pull request

В описании укажите:

- что после изменения увидит пользователь или интегратор;
- что намеренно осталось за пределами задачи;
- изменились ли публичные контракты CLI, JSON или HTTP;
- какая документация обновлена;
- какие команды проверки выполнены.

Не добавляйте тяжёлые фреймворки и скрытые зависимости времени выполнения.
Выбирайте минимальное изменение, которое сохраняет безопасность путей,
целостность данных, доступность интерфейса и опубликованные контракты.
