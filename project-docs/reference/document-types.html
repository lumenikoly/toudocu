#Продукт и архитектура

Вид и расположениеЗачем нуженКогда создаватьНе использовать для
Architecture Overview — architecture/overview.mdОпределяет границу системы и служит картой архитектурных вопросовВсегда; overview напрямую ссылается на каждый подробный документ архитектурыПолного описания всех взаимодействий, контрактов и локальных правил
Архитектура — другие architecture/**/*.mdКратко отвечает на один доказуемый архитектурный вопросКогда ответ затрагивает устройство системы, границы или зависимости нескольких частейПоследовательности запроса, API-формата, процедуры, ADR или правил одного модуля
Модуль — modules/*.md, ID MOD-*Фиксирует стабильную границу ответственности, бизнес-правила и инвариантыКогда такая граница важна продукту, владельцам или связанным сценариямЗеркала каталога исходного кода или перечня внутренних функций
Пользовательский сценарий — use-cases/*.md, ID UC-*Описывает наблюдаемое поведение актора и ожидаемый результатКогда поведение должно быть связано с модулем, правилами, экранами или roadmapРеализационного call graph и пошаговой эксплуатационной инструкции
Процесс — flows/*.md, ID FLOW-*Визуализирует один повторно используемый сценарий, ветку ошибки или межсистемное взаимодействиеКогда Mermaid-схема действительно упрощает понимание use case или архитектурыВсеобъемлющей схемы кода или замены текстовых требований
Экран — screens/SC-*.md, ID SC-* и TR-*Описывает значимый экран, его состояния и исходящие пользовательские переходыКогда продукту нужны каталог экранов, Screen Map или traceabilityТехнического route, layout, redirect либо внутреннего состояния компонента
Архитектурное решение — decisions/*.md, ID ADR-*Сохраняет контекст, принятое решение и его последствияКогда решение и рассмотренный компромисс действительно были зафиксированыРетроспективного оправдания текущего кода или описания устройства системы

Специальный путь определяет Document.Type, но сам по себе не обещает наличие entity ID. Уникальность ID и явные связи дополнительно проверяются у MOD-*, UC-*, FLOW-*, SC-*/TR-*, ADR-* и других видов, для которых они явно заданы. status.md, roadmap.md, risks.md и архитектурные документы имеют специальное поведение без собственного уникального entity ID. Ни один из этих видов не следует создавать только ради дополнительной страницы портала или отсутствия предупреждений.

Контракт — contracts/Фиксирует внешний интерфейс, команду, API, schema или формат обменаКогда потребителю нужна точная и стабильная граница взаимодействияОбучающей последовательности, архитектурного объяснения или списка фактов
Стандарт — quality/STD-*.md, ID STD-*Задаёт обязательные и проверяемые правила проектаКогда правило имеет область действия, владельца и способ проверкиСоветов без обязательной силы или разовой процедуры
Runbook — runbooks/RB-*.md, ID RB-*Даёт безопасную эксплуатационную процедуру с проверкой и откатомТолько для реально выполняемой операции с известными средой и рискомОбщего руководства, продуктового flow или вымышленной процедуры
Руководство — guides/Помогает читателю достичь конкретного результатаДля установки, настройки или выполнения последовательности действийЭнциклопедического каталога фактов и нормативного контракта
Справочник — reference/Собирает факты, варианты и параметры для быстрого поискаКогда читатель уже понимает задачу и ищет точное значение или выборПошагового обучения, обоснования решения или текущего статуса

Подробные требования к STD-*, RB-* и custom-разделам находятся в руководстве по стандартам и runbooks. Форматы CLI и HTTP остаются в контрактах, а не дублируются здесь.

#Рабочие и свободные документы

Вид и расположениеЗачем нуженКогда создаватьНе использовать для
Рабочая задача — work/TASK-*.mdОпределяет разрешённый объём работы, результат, критерии приёмки и проверкуДля существенной работы, которой нужен проверяемый контракт и handoff агенту или CIЛюбого небольшого запроса, общего roadmap или описания уже существующей функции
Дефект — work/BUG-*.mdФиксирует наблюдаемое расхождение и данные для его воспроизведения; по мере готовности добавляет причину и регрессионную проверкуКогда поведение действительно не совпадает с ожидаемымИдеи, исследовательской задачи или неподтверждённого предположения об ошибке
Custom-раздел — неизвестный верхнеуровневый каталогДаёт проекту собственную группу документов без новой встроенной семантикиКогда ни один встроенный раздел не выражает устойчивую предметную областьМаскировки уже существующего встроенного типа
Обычный Markdown — любой другой безопасный путьПередаёт полезное знание без typed-контрактаКогда достаточно текста, ссылок и базовой проверкиОбъявления машинных связей, которые Docu-docu должен валидировать

Активные work items находятся в work/, а завершённые и отменённые могут быть перемещены командой Docu-docu в work/archive/YYYY/. Полный контракт описан в руководстве по рабочим задачам.

#Тип документа и тип задачи — не одно и то же

Любой TASK-* или BUG-* является документом вида Рабочая задача. Поле Тип внутри него дополнительно определяет характер работы:

Значение ТипЗначение
FeatureНовое или изменённое пользовательское поведение
BugИсправление наблюдаемого дефекта; использует ID BUG-* и обязательные данные воспроизведения
MaintenanceТехническое обслуживание без обязательного нового поведения
DocumentationИзменение документации как основной результат
ResearchИсследование с проверяемым результатом, но без заранее обещанной реализации

Draft использует сокращённый контракт. Начиная с любого non-Draft статуса Feature связывается с use case; Maintenance, Documentation и Research без use case объясняют, почему сценарий не применяется. Для non-Draft Bug требуются связанный use case либо явное объяснение Не применяется, раздел причины и регрессионное покрытие; у выполненного бага причина уже должна быть установлена. Поле Тип не превращает work item в модуль, руководство или иной вид документа.

#Вспомогательные источники и manifests

  • screens/hotspots.json дополняет существующие SC-* и TR-*

интерактивными областями в процентах; это не самостоятельный Markdown-документ.

  • screens/index.md является входной страницей встроенного раздела экранов и

получает отдельный machine type screen-index; это не SC-*-сущность.

  • quality/index.md и runbooks/index.md задают входные страницы своих

разделов. Manifest неизвестного раздела дополнительно объявляет Тип: Custom, владельца и описание.

  • screens/map.md считается устаревшим источником. Каталог, Screen Map и

playable flows строятся из screens/SC-*.md; отдельную карту вручную вести не нужно.

  • Generated HTML, report.json и поисковый индекс являются производными

результатами. Их не редактируют как источник истины.

#Главное правило выбора

Сначала сформулируйте полезный вопрос читателя, затем выберите вид документа. Если проекту не нужны стабильный ID, проверяемые связи или специальное представление, оставьте материал обычным Markdown. Структурная проверка подтверждает заявленный контракт, но не делает ненужный документ полезным.
