UC-TASK-02 · Проверить рабочую задачу

Исполнитель сначала получает план проверок без выполнения, а затем при явном выборе запускает все или один target и получает полный отчёт.

Исполнитель сначала получает план проверок без выполнения, а затем при явном выборе запускает все или один target и получает полный отчёт.

#Входные данные

  • стабильный TASK-* ID;
  • каталог документации и repository root;
  • timeout каждой команды;
  • режим --dry-run или --run;
  • необязательный target AC-*, ALL или DOCS;
  • необязательный путь JSON-отчёта.

#Предусловия

  • для --run задача подготовлена как минимум до статуса Готово к работе;
  • --dry-run разрешён для полного Draft и не исполняет команды;
  • владелец репозитория доверяет командам из раздела Проверка;
  • исполнитель осознаёт, что команды запускаются с его правами.

#Основной сценарий

  1. Исполнитель вызывает

docgent task verify TASK-ID ./docs --dry-run --format json.

  1. Docgent находит задачу и применяет к ней task-local validation gate.
  2. Docgent составляет список уникальных команд AC-*, ALL и DOCS.
  3. Dry-run возвращает команды со status planned, ничего не выполняя.
  4. После проверки плана исполнитель явно вызывает task verify --run.
  5. Docgent последовательно запускает выбранные команды из repository root.
  6. Docgent связывает результаты команд с критериями и формирует

TaskVerifyReport.

  1. Исполнитель использует итоговый status, exit code и вывод команд для

принятия результата.

#Ошибочные сценарии

  • отсутствующий или неоднозначный ID завершает команду с кодом 1;
  • Draft и Cancelled блокируют --run без выполнения команд;
  • ошибка контракта выбранной задачи блокирует запуск всех команд и даёт status

blocked;

  • команда, которую невозможно запустить, получает status start_error;
  • ненулевой exit code команды даёт ей status failed;
  • превышение timeout завершает дерево процессов и даёт status timed_out;
  • ошибка одной команды не останавливает остальные проверки;
  • ошибка записи --report даёт ненулевой exit code, даже если проверки прошли.

#Постусловия

Dry-run не имеет внешних эффектов. В режиме run все выбранные команды получили результат, если validation gate не заблокировал запуск. Итоговый status равен planned, passed, failed или blocked; exit code 0 возвращается для planned и passed. Команды в режиме run могут изменять репозиторий, поскольку выполняются как обычный доверенный код.

#Бизнес-правила

Правила определены в документах соответствующих модулей:

  • BR-CLI-002 — проверки запускаются только явно.
  • BR-CLI-003 — timeout завершает дерево процессов.
  • BR-MODEL-003 — готовая к работе задача имеет полный проверяемый контракт.

#Проверка

  • fake runner для дедупликации, ошибок запуска и продолжения после ошибки;
  • реальный Unix-тест завершения process group;
  • JSON-тест матрицы критериев и результатов команд;
  • проверка task-local validation gate;
  • Windows amd64 cross-build.
