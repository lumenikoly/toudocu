Рабочие задачи

Docgent хранит каждый рабочий элемент в отдельном файле work/ .md . Функциональность, обслуживание, документация и исследования используют TASK- , а баги — BUG- . Все типы остаются одной сущностью WorkItem , используют общие статусы, зависимости, команды context/verify и годовой архив.

Docgent хранит каждый рабочий элемент в отдельном файле work/*.md. Функциональность, обслуживание, документация и исследования используют TASK-*, а баги — BUG-*. Все типы остаются одной сущностью WorkItem, используют общие статусы, зависимости, команды context/verify и годовой архив.

#Минимальный черновик

В одном файле должна находиться ровно одна задача. Заголовок начинается с уникального TASK-*:

md
# TASK-AUTH-014: Добавить восстановление пароля

- Статус: Черновик
- Тип: Feature

## Результат

Пользователь может запросить ссылку для восстановления пароля.

Для черновика обязательны корректные Статус, Тип и непустой раздел Результат. Остальные поля и разделы можно добавить позже.

#Статусы

СтатусКогда использоватьДополнительные правила
ЧерновикЗадача ещё уточняетсяДостаточно типа и результата
Готово к работеКонтракт задачи согласованОбязательны все рабочие разделы и проверки AC-*
В работеИзменения выполняютсяДействуют те же требования, что для готовой задачи
ЗаблокированоРаботу нельзя продолжитьТребуется непустой раздел Блокер
ВыполненоРабота принятаВсе AC-* отмечены; обязательны ALL и DOCS; зависимости завершены
ОтмененоЗадача больше не нужнаТребуется непустой раздел Причина отмены

В Markdown также принимаются английские значения draft, ready, in progress, blocked, done/completed и cancelled/canceled.

#Типы

Тип описывает характер изменения, а не его состояние.

ЗначениеСмыслСвязанный сценарий
FeatureНовая или изменённая пользовательская функциональностьОбязателен
BugИсправление пользовательской ошибкиОбязателен
MaintenanceРефакторинг, инфраструктура и техническое обслуживаниеНеобязателен
DocumentationИзменение документацииНеобязателен
ResearchИсследование или проверка гипотезыНеобязателен

Для технического типа без поля Сценарий нужен непустой раздел Обоснование отсутствия сценария. Если сценарий указан для любого типа, его UC-* должен существовать.

В Markdown можно использовать русские значения Функциональность, Ошибка, Обслуживание, Документация и Исследование. В отчётах они нормализуются к английским значениям из таблицы.

task init --type Bug создаёт work/BUG-AREA-NNN.md; остальные типы получают TASK-AREA-NNN. Для Тип: Bug префикс BUG- обязателен, а BUG-* нельзя использовать с другим типом.

#Специальный контракт бага

Баг сначала фиксирует существование дефекта, а затем доказывает исправление того же сценария. Для него всегда обязательны поля Серьёзность, Приоритет, Воспроизводимость, Регрессия, Модуль, Сценарий, Владелец и Последнее обновление.

ПолеДопустимые значения
СерьёзностьКритическая, Высокая, Средняя, Низкая
ПриоритетСрочный, Высокий, Обычный, Низкий
ВоспроизводимостьВсегда, Часто, Иногда, Редко, Не воспроизводится, Неизвестно
РегрессияДа, Нет

Серьёзность описывает последствия, а приоритет — порядок работы; Docgent не вычисляет одно поле из другого. Для Регрессия: Да в документе указывается версия или период проявления.

Даже черновик бага содержит непустые разделы Симптом, Ожидаемое поведение и Фактическое поведение, а также непустые Шаги воспроизведения или Доказательства. Начиная с Готово к работе, дополнительно обязательны Причина, Область изменения, Не входит в исправление, План, Критерии приёмки, Проверка и Влияние на документацию.

Если причина ещё не подтверждена, следует писать Не установлена и вынести предположения в отдельный раздел Гипотезы. У выполненного бага причина уже должна быть установлена. План бага оформляется нумерованным списком без чекбоксов; чекбоксы остаются только у AC-*.

Для готового к работе бага нужен критерий, явно проверяющий регрессионный тест. Если автоматизация технически невозможна, причина и точный ручной сценарий описываются в непустом разделе Регрессионный тест.

Технический дефект может использовать Сценарий: Не применяется, но тогда обязателен непустой раздел Связь с пользовательским поведением. Указанные MOD-*, UC-*, SC-*, TR-* и зависимости должны существовать.

Доказательства не должны содержать пароли, токены, ключи, персональные данные или необработанные production-дампы с чувствительными данными.

#Поля задачи

ПолеТребование
СтатусОбязательно всегда; значение из таблицы статусов
ТипОбязательно всегда; значение из таблицы типов
МодульОбязателен начиная с Готово к работе; MOD-* должен существовать
СценарийОбязателен для Feature и Bug; указанный UC-* должен существовать
ПроцессНеобязательная ссылка на существующий FLOW-*; добавляется в task context
СтандартыНеобязательный список существующих STD-*; требует target QUALITY
Затронутые runbooksНеобязательный список существующих RB-*; добавляется в task context
Зависит отНеобязательный список TASK-* и BUG-* через пробел, запятую или точку с запятой
ПриоритетНеобязательная метка; фиксированного набора значений нет
ВладелецНеобязательное имя команды или ответственного
Последнее обновлениеНеобязательная дата, используемая проверкой устаревания

Идентификаторы задач должны быть уникальны. Зависимости должны существовать и не образовывать циклов. Задачу нельзя перевести в Выполнено, пока хотя бы одна её зависимость не выполнена.

#Архив

Активные задачи находятся в корне work/. Завершённые и отменённые задачи можно перемещать в годовой архив:

text
work/TASK-AUTH-014.md
work/BUG-AUTH-021.md
work/archive/2026/TASK-AUTH-009.md

Используйте команды, а не ручное перемещение:

bash
docgent task archive TASK-AUTH-009 ./docs --format json
docgent task restore TASK-AUTH-009 ./docs --format json

Архивирование разрешено только для Done/Выполнено и Cancelled/Отменено. Команда проверяет контракт, безопасный путь, конфликт назначения, входящие Markdown-ссылки и относительные ссылки самой задачи. При риске разрыва ссылки файл остаётся на месте. Содержимое и статус задачи команда не меняет.

task restore возвращает файл из work/archive/YYYY/ в work/. Оно также доступно для ошибочно помещённой в архив активной задачи, чтобы восстановить корректную структуру. Идентификаторы TASK-*/BUG-* и зависимости действуют глобально во всём work/**; task init не переиспользует архивные номера.

#Обязательные разделы

Начиная со статуса Готово к работе, задача содержит непустые разделы:

  1. Результат — наблюдаемый итог работы.
  2. Изменение поведения с подразделами Было и Станет — обязательно для

Feature; Bug использует отдельные разделы из специального контракта.

  1. Область изменения — файлы и каталоги, которые разрешено менять.
  2. Не входит в задачу — явно исключённая работа.
  3. Критерии приёмки — проверяемые условия с ID AC-*.
  4. План — предполагаемая последовательность работы.
  5. Проверка — команды для критериев, а также ALL и DOCS.
  6. Влияние на документацию — что нужно обновить или почему обновление не нужно.

Пути в Области изменения, записанные в обратных кавычках, проверяются относительно --repository-root. Путь не может выходить за корень репозитория и должен существовать. Новый отсутствующий файл разрешён, если существует его безопасный родительский каталог. Glob-шаблоны обязаны находить совпадения.

#Критерии и проверки

Чекбоксы разрешены в разделах Критерии приёмки и План. Каждый критерий начинается с уникального локального ID AC-*:

md
## Критерии приёмки

- [ ] `AC-01` Неверный токен возвращает ошибку `INVALID_TOKEN`.
- [ ] `AC-02` Действительный токен позволяет сменить пароль.

Для каждого критерия нужна ровно одна запись в разделе Проверка. Одна запись ссылается ровно на один target и содержит хотя бы одну команду:

md
## Проверка

- `AC-01` → `go test ./internal/auth -run TestInvalidToken`
- `AC-02` → `go test ./internal/auth -run TestResetPassword`
- `ALL` → `go test ./...`
- `DOCS` → `docgent check ./docs --strict`

Targets имеют следующий смысл:

TargetЧто подтверждает
AC-*Отдельный критерий приёмки
ALLПолная проверка проекта
DOCSПолная проверка документации
QUALITYПроверка явно связанных стандартов командами самой задачи

Readiness требует ровно одну команду для каждого AC-*, ALL и DOCS. При непустом Стандарты дополнительно требуется ровно один QUALITY, а full verification означает ALL + DOCS + QUALITY. task context включает явно связанные standards и runbooks в typed collections, documents и requiredReads; автоматического сопоставления области стандарта со scope нет. Для статуса Выполнено все критерии должны быть отмечены [x].

#Полный пример

md
# TASK-AUTH-014: Добавить восстановление пароля

- Статус: Готово к работе
- Тип: Feature
- Приоритет: Высокий
- Модуль: MOD-AUTH
- Сценарий: UC-AUTH-03
- Процесс: FLOW-AUTH-RECOVERY
- Владелец: Команда Identity
- Зависит от: TASK-MAIL-004
- Последнее обновление: 2026-07-27

## Результат

Пользователь может безопасно восстановить пароль по одноразовой ссылке.

## Изменение поведения

### Было

Пользователь не может самостоятельно восстановить забытый пароль.

### Станет

Пользователь восстанавливает пароль по одноразовой ссылке.

## Область изменения

- `internal/auth/`;
- `internal/mail/`;
- `docs/modules/auth.md`.

## Не входит в задачу

- изменение правил регистрации;
- новый почтовый провайдер.

## Критерии приёмки

- [ ] `AC-01` Просроченный токен отклоняется.
- [ ] `AC-02` Действительный токен позволяет сменить пароль один раз.

## План

- [ ] Добавить выпуск и хранение токена.
- [ ] Реализовать проверку срока и одноразового использования.
- [ ] Обновить документацию модуля.

## Проверка

- `AC-01` → `go test ./internal/auth -run TestExpiredResetToken`
- `AC-02` → `go test ./internal/auth -run TestResetTokenSingleUse`
- `ALL` → `go test ./...`
- `DOCS` → `docgent check ./docs --strict`

## Влияние на документацию

Обновить сценарий восстановления пароля и правила модуля авторизации.

#Выполнение команд

task ready проверяет полный Draft без изменения статуса. task context собирает сведения начиная с Ready. task verify --dry-run возвращает план, а task verify --run после локального gate последовательно выполняет выбранные команды из корня репозитория.

Одинаковые команды выполняются один раз, даже если связаны с несколькими targets. Ошибка одной команды не останавливает остальные. Команды считаются доверенным кодом репозитория и выполняются с правами текущего пользователя.

Подробности форматов отчёта и exit codes находятся в CLI-контракте.
