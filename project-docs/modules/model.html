Проектная модель и валидация

Модуль читает каталог документации, строит связанную модель проекта и формирует диагностику структуры, идентификаторов, путей и зависимостей.

Модуль читает каталог документации, строит связанную модель проекта и формирует диагностику структуры, идентификаторов, путей и зависимостей.

#Назначение

Преобразовать набор независимых Markdown-файлов в предсказуемую модель, пригодную для проверки, HTML-рендеринга и машинного отчёта.

#Расположение в коде

  • модель документов: internal/app/docs_core.go, internal/app/types.go;
  • знания и work items: internal/app/knowledge.go;
  • разрешение ссылок: internal/app/documentation_links.go;
  • общие безопасные операции с путями: internal/app/utils.go.

#Границы

Модуль не генерирует HTML-файлы и не запускает команды задач. Он возвращает модель и diagnostics, не изменяя исходную документацию. Editor может передать один in-memory overlay для preview/validation; обычный публичный build модели по-прежнему читает filesystem snapshot.

#Бизнес-правила

#BR-MODEL-001: Roadmap является единственным источником глобального охвата

Глобальный прогресс учитывает только элементы roadmap.md. Для связанного UC-* выполнение берётся из статуса use case, а CON-* и DLV-* сохраняют состояние собственного checkbox.

#BR-MODEL-002: Ссылки не выходят за repository root

Локальная ссылка может покинуть каталог документации только внутри явно определённого repository root. Выход за его границы блокируется и отражается в diagnostics.

#BR-MODEL-003: Готовая к работе задача имеет полный проверяемый контракт

Начиная со статуса «Готово к работе», work item содержит scope, ограничения, критерии AC-*, план, команды проверки и влияние на документацию.

#BR-MODEL-004: Документы экранов являются источником графа

Метаданные, состояния и таблицы переходов из screens/SC-*.md образуют типизированную модель SC-* и TR-*. Произвольная Mermaid-грамматика не разбирается как требования или связи.

#BR-MODEL-005: Overview является прямой картой архитектурных вопросов

architecture/overview.md обязателен и имеет тип Architecture Overview. Каждый другой Markdown-файл под architecture/ задаёт один непустой архитектурный вопрос и напрямую связан из overview; транзитивная ссылка не считается листингом.

#BR-MODEL-006: OpenAPI contracts проверяются как отдельный source type

Только contracts/**/*.openapi.{yaml,yml,json} получает встроенную OpenAPI 3.0/3.1 validation. Проверяются root fields, operations/responses, уникальность operationId, path parameters и internal $ref; external references никогда не загружаются. Произвольный YAML не получает выдуманной schema.

#Инварианты

  • каждый стабильный ID уникален в своей проектной модели;
  • стандарты STD-* и runbook RB-* уникальны, а work item ссылается только на существующие typed documents;
  • минимальная документация требует index.md и architecture/overview.md; manifest появившегося quality, runbooks или custom-раздела проверяется предупреждениями;
  • архитектурные broken/blocked links являются errors, а форма непустого вопроса остаётся semantic review;
  • экранные переходы ссылаются только на существующие SC-*;
  • screen routes уникальны, а previews и hotspots не выходят за repository root;
  • каждый проигрываемый сценарий достигает terminal screen либо содержит diagnostic;
  • один файл work/*.md содержит ровно один рабочий элемент TASK-* или BUG-*;
  • номера строк в публичных отчётах начинаются с единицы;
  • OpenAPI issue аддитивно содержит column, когда parser знает позицию;
  • обычная сборка модели не выполняет команды;
  • вычисляемое состояние никогда не перезаписывает исходные Markdown-файлы; пользовательская запись в serve остаётся отдельной workspace-операцией.

#Стабильные интерфейсы

  • BuildDocumentationModel(Options) и остальные экспорты корневого api.go;
  • ProjectReport schema v1;
  • архитектурные документы сохраняют documents[].type = architecture;
  • documents[].sectionType аддитивно передаёт стабильный встроенный раздел;
  • коды Issue;
  • правила ID и структуры, описанные в CLI-контракте;
  • статусы, типы и формат задач из руководства по рабочим задачам;
  • стандарты качества.
