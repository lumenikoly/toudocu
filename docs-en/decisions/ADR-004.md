# ADR-004: OpenAPI and Markdown describe the HTTP API together


The wire-level HTTP API contract is stored in OpenAPI 3.1.0, while behavior and
trust boundaries are stored in a companion Markdown document.

<!-- toudocu:section context -->
## Context

Endpoint tables and manually repeated JSON shapes in Markdown drift from
handlers and are ill-suited to automated parity checks. At the same time,
OpenAPI cannot fully express atomic filesystem behavior, the local trust model,
comparison semantics, or boundaries among generated, canonical, and
translation portals.

<!-- toudocu:section decision -->
## Decision

Files matching `contracts/**/*.openapi.{yaml,yml,json}` are a distinct validated
source type. For Editor and Changes, YAML owns paths, methods, parameters,
headers, statuses, media types, examples, and JSON schemas. Declarative route
registries are checked bidirectionally against operations.

Companion Markdown documents do not repeat wire shapes and instead own
behavior, security, filesystem, and failure-isolation invariants. Internal
`$ref` values are validated locally; external references are not loaded.
Canonical `serve` presents the contracts through a vendored offline Swagger UI;
static build copies the specs themselves but not the UI.

<!-- toudocu:section consequences -->
## Consequences

- A handler change requires coordinated changes to the registry, OpenAPI, and
  tests.
- `check` and editor diagnostics validate OpenAPI identically with line/column.
- `ProjectReport` remains schemaVersion 1, while a positional issue gains an
  additive optional `column`.
- Translation roots do not become contract sources for ordinary workflows.
- Swagger UI does not expand the runtime trust boundary or add a CDN.
