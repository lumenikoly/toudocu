# Просмотр изменений

Toudocu берёт обе версии файла из локального Git-репозитория. Он не выполняет
`fetch`, не переключает ветки и не меняет историю, ссылки, индекс или рабочие
файлы. Интерактивный раздел доступен только при `serve`; результат обычного
`build` остаётся статическим и не зависит от истории Git.

## Путь в локальном портале

1. Из корня репозитория запустите:

   ```bash
   toudocu serve ./docs
   ```

2. Откройте адрес, который вывела команда, и перейдите в раздел «Изменения».
   Прямой путь — `/changes/`.
3. Оставьте диапазон `HEAD → working-tree`, если нужно проверить все текущие
   локальные правки. Для другого сравнения раскройте диапазон и укажите начало
   и конец явно.
4. Найдите файл по имени или сузьте список по состоянию, области и типу. Фильтр
   «Тип» умеет показать все файлы, только документацию или только остальные
   файлы репозитория.
5. Выберите файл и начните с вкладки «Diff»: это точный патч Git. Вкладка «Файл
   целиком» удобна, когда нужен контекст за пределами изменённых строк.
6. Для Markdown при необходимости откройте «До и после», «Семантика» или
   «Связи». Специальные вкладки OpenAPI, Mermaid, ресурсов и карты экранов
   появляются только для подходящих файлов.
7. Если нужно обсудить документацию с агентом, создайте вопрос либо запрос на
   изменение и пройдите путь из
   [сценария обратной связи с агентом](../use-cases/UC-AGENT-FEEDBACK-01.md).

## Что именно сравнивается

По умолчанию диапазон `HEAD → working-tree` включает всё, что видно в рабочем
дереве: изменения в индексе, изменения вне индекса, удаления и новые файлы.
Также можно сравнить:

- `HEAD` с индексом;
- любой локальный коммит или ссылку с другим коммитом;
- коммит с рабочим деревом;
- общую базу выбранной ветки и `HEAD` с рабочим деревом через `--branch-base`.

На странице всегда видны исходно введённые значения и ссылки Git, в которые они
разрешились. Toudocu не загружает удалённые ветки. Если нужной ссылки нет
локально, сначала получите её обычными средствами Git.

Для вложенного проекта `--repository-root` выбирает каталог с его
`.toudocu/config.yml`. Пути из `changes.exclude` считаются относительно этого
каталога.

## Представления файла

| Представление | Когда использовать | Что показывает |
|---|---|---|
| «Diff» | Быстрая проверка точных правок | Патч Git с номерами старых и новых строк. Можно переключиться между единым видом и двумя сторонами, перейти между фрагментами и скопировать патч |
| «Файл целиком» | Нужен весь контекст | Текущую версию текстового UTF-8 файла; для удалённого файла — версию до удаления. Выделенный фрагмент можно скопировать или прокомментировать |
| «До и после» | Важно увидеть готовый Markdown | Безопасно отрисованные старую и новую версии. Добавленные, удалённые, изменённые и перемещённые разделы отмечены отдельно |
| «Семантика» | Изменились структура или известные поля | Различия заголовков, метаданных, критериев задач, правил, переходов и связей. Одно форматирование без изменения модели сюда не попадает |
| «Связи» | Документ ссылается на другие сущности | Добавленные и удалённые связи между известными документами |

Если Markdown одной стороны разобрать не удалось, вкладка «Diff» продолжает
работать, а ошибка остаётся в дополнительном представлении. Двоичный или
слишком большой файл получает понятное сообщение и доступные сведения о размере
вместо попытки вывести содержимое.

Специальные представления уточняют результат:

- OpenAPI сравнивает операции, параметры, тела запросов, ответы, схемы и
  настройки безопасности. Потенциально несовместимые изменения помечаются, но
  окончательное решение остаётся за разработчиком;
- Mermaid сопоставляет блоки по `%% id: <stable-id>` либо по разделу и порядку,
  независимо строит обе диаграммы и показывает разницу исходного текста;
- PNG, JPEG, WebP и SVG показываются рядом с размером и геометрией. Два
  растровых изображения можно наложить друг на друга ползунком;
- изменения `SC-*` и `TR-*` отображаются поверх карты экранов, включая удалённые
  элементы из старой версии.

## Отчёт в терминале и CI

Базовые примеры:

```bash
toudocu changes ./docs --format text
toudocu changes ./docs --base main --target working-tree --format json
toudocu changes ./docs --branch-base main --format markdown
toudocu changes file docs/modules/MOD-AUTH.md --base HEAD --target index
toudocu task changes TASK-AUTH-015 ./docs --format json
```

После построения отчёта его можно сузить:

| Флаг | Что останется в отчёте |
|---|---|
| `--status STATUS` | Файлы в состоянии `added`, `untracked`, `modified`, `deleted` или `renamed` |
| `--module VALUE` | Пути, сущности или описания, совпавшие с указанным модулем |
| `--type TYPE` | Сущности выбранного типа: например `module`, `use-case`, `flow`, `screen` или `task` |
| `--permanent-only` | Только долговременная проектная документация, без задач, контрактов и ресурсов |
| `--include-assets` | Двоичные ресурсы, даже если они отключены настройкой `changes.includeAssets` |
| `--translation-input` | Все читательские Markdown-файлы, рабочие документы и ресурсы, нужные процессу перевода |

Фильтры можно сочетать. Форматы `text`, `json` и `markdown` используют один и
тот же отфильтрованный результат; `-o FILE` записывает его в файл.

Коды завершения:

- `0` — отчёт построен без ошибок;
- `1` — отчёт построен, но содержит ошибку анализа;
- `2` — диапазон Git задан неверно;
- `3` — Git недоступен или репозиторий не найден;
- `4` — внутренняя ошибка Toudocu.

## Изменения, заявленные задачей

В `TASK-*` поле «Влияние на документацию» перечисляет файлы, которые задача
обещает изменить. Команда

```bash
toudocu task changes TASK-AUTH-015 ./docs
```

сопоставляет этот список с текущим Git diff. Она предупреждает о незаявленном
файле, об обещанном, но неизменённом файле и о документе, который должен был
появиться, но не появился. Это повод перечитать задачу и diff, а не
автоматическое доказательство ошибки.

Процесс `$toudocu translate` использует тот же отчёт как входные данные, но не
меняет его схему. Точный патч Git всегда остаётся основным источником: любые
отрисованные и семантические представления только помогают его прочитать.

Точные поля HTTP и JSON описаны в [HTTP-контракте](../contracts/changes-http.md)
и [справочнике отчёта](../reference/changes-report.md). Границы чтения Git — в
[архитектурном документе](../architecture/documentation-changes.md).
