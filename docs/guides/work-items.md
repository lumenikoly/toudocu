# Рабочие задачи

Docgent хранит каждую рабочую задачу в отдельном файле
`work/TASK-*.md`. Задача описывает ожидаемый результат, допустимую область
изменений, критерии приёмки и команды проверки.

## Минимальный черновик

В одном файле должна находиться ровно одна задача. Заголовок начинается с
уникального `TASK-*`:

```md
# TASK-AUTH-014: Добавить восстановление пароля

- Статус: Черновик
- Тип: Feature

## Результат

Пользователь может запросить ссылку для восстановления пароля.
```

Для черновика обязательны корректные `Статус`, `Тип` и непустой раздел
`Результат`. Остальные поля и разделы можно добавить позже.

## Статусы

| Статус | Когда использовать | Дополнительные правила |
|---|---|---|
| `Черновик` | Задача ещё уточняется | Достаточно типа и результата |
| `Готово к работе` | Контракт задачи согласован | Обязательны все рабочие разделы и проверки `AC-*` |
| `В работе` | Изменения выполняются | Действуют те же требования, что для готовой задачи |
| `Заблокировано` | Работу нельзя продолжить | Требуется непустой раздел `Блокер` |
| `Выполнено` | Работа принята | Все `AC-*` отмечены; обязательны `ALL` и `DOCS`; зависимости завершены |
| `Отменено` | Задача больше не нужна | Требуется непустой раздел `Причина отмены` |

В Markdown также принимаются английские значения `draft`, `ready`,
`in progress`, `blocked`, `done`/`completed` и `cancelled`/`canceled`.

## Типы

Тип описывает характер изменения, а не его состояние.

| Значение | Смысл | Связанный сценарий |
|---|---|---|
| `Feature` | Новая или изменённая пользовательская функциональность | Обязателен |
| `Bug` | Исправление пользовательской ошибки | Обязателен |
| `Maintenance` | Рефакторинг, инфраструктура и техническое обслуживание | Необязателен |
| `Documentation` | Изменение документации | Необязателен |
| `Research` | Исследование или проверка гипотезы | Необязателен |

Для технического типа без поля `Сценарий` нужен непустой раздел
`Обоснование отсутствия сценария`. Если сценарий указан для любого типа, его
`UC-*` должен существовать.

В Markdown можно использовать русские значения `Функциональность`, `Ошибка`,
`Обслуживание`, `Документация` и `Исследование`. В отчётах они нормализуются к
английским значениям из таблицы.

## Поля задачи

| Поле | Требование |
|---|---|
| `Статус` | Обязательно всегда; значение из таблицы статусов |
| `Тип` | Обязательно всегда; значение из таблицы типов |
| `Модуль` | Обязателен начиная с `Готово к работе`; `MOD-*` должен существовать |
| `Сценарий` | Обязателен для `Feature` и `Bug`; указанный `UC-*` должен существовать |
| `Процесс` | Необязательная ссылка на существующий `FLOW-*`; добавляется в task context |
| `Зависит от` | Необязательный список `TASK-*` через пробел, запятую или точку с запятой |
| `Приоритет` | Необязательная метка; фиксированного набора значений нет |
| `Владелец` | Необязательное имя команды или ответственного |
| `Последнее обновление` | Необязательная дата, используемая проверкой устаревания |

Идентификаторы задач должны быть уникальны. Зависимости должны существовать и
не образовывать циклов. Задачу нельзя перевести в `Выполнено`, пока хотя бы одна
её зависимость не выполнена.

## Обязательные разделы

Начиная со статуса `Готово к работе`, задача содержит непустые разделы:

1. `Результат` — наблюдаемый итог работы.
2. `Изменение поведения` с подразделами `Было` и `Станет` — обязательно для
   Feature и Bug.
3. `Область изменения` — файлы и каталоги, которые разрешено менять.
4. `Не входит в задачу` — явно исключённая работа.
5. `Критерии приёмки` — проверяемые условия с ID `AC-*`.
6. `План` — предполагаемая последовательность работы.
7. `Проверка` — команды для критериев, а также `ALL` и `DOCS`.
8. `Влияние на документацию` — что нужно обновить или почему обновление не нужно.

Пути в `Области изменения`, записанные в обратных кавычках, проверяются
относительно `--repository-root`. Путь не может выходить за корень репозитория и
должен существовать. Новый отсутствующий файл разрешён, если существует его
безопасный родительский каталог. Glob-шаблоны обязаны находить совпадения.

## Критерии и проверки

Чекбоксы разрешены в разделах `Критерии приёмки` и `План`. Каждый критерий
начинается с уникального локального ID `AC-*`:

```md
## Критерии приёмки

- [ ] `AC-01` Неверный токен возвращает ошибку `INVALID_TOKEN`.
- [ ] `AC-02` Действительный токен позволяет сменить пароль.
```

Для каждого критерия нужна ровно одна запись в разделе `Проверка`. Одна запись
ссылается ровно на один target и содержит хотя бы одну команду:

```md
## Проверка

- `AC-01` → `go test ./internal/auth -run TestInvalidToken`
- `AC-02` → `go test ./internal/auth -run TestResetPassword`
- `ALL` → `go test ./...`
- `DOCS` → `docgent check ./docs --strict`
```

Targets имеют следующий смысл:

| Target | Что подтверждает |
|---|---|
| `AC-*` | Отдельный критерий приёмки |
| `ALL` | Полная проверка проекта |
| `DOCS` | Полная проверка документации |

Readiness требует ровно одну команду для каждого `AC-*`, `ALL` и `DOCS`.
Для статуса `Выполнено` все критерии должны быть отмечены `[x]`.

## Полный пример

```md
# TASK-AUTH-014: Добавить восстановление пароля

- Статус: Готово к работе
- Тип: Feature
- Приоритет: Высокий
- Модуль: MOD-AUTH
- Сценарий: UC-AUTH-03
- Процесс: FLOW-AUTH-RECOVERY
- Владелец: Команда Identity
- Зависит от: TASK-MAIL-004
- Последнее обновление: 2026-07-27

## Результат

Пользователь может безопасно восстановить пароль по одноразовой ссылке.

## Изменение поведения

### Было

Пользователь не может самостоятельно восстановить забытый пароль.

### Станет

Пользователь восстанавливает пароль по одноразовой ссылке.

## Область изменения

- `internal/auth/`;
- `internal/mail/`;
- `docs/modules/auth.md`.

## Не входит в задачу

- изменение правил регистрации;
- новый почтовый провайдер.

## Критерии приёмки

- [ ] `AC-01` Просроченный токен отклоняется.
- [ ] `AC-02` Действительный токен позволяет сменить пароль один раз.

## План

- [ ] Добавить выпуск и хранение токена.
- [ ] Реализовать проверку срока и одноразового использования.
- [ ] Обновить документацию модуля.

## Проверка

- `AC-01` → `go test ./internal/auth -run TestExpiredResetToken`
- `AC-02` → `go test ./internal/auth -run TestResetTokenSingleUse`
- `ALL` → `go test ./...`
- `DOCS` → `docgent check ./docs --strict`

## Влияние на документацию

Обновить сценарий восстановления пароля и правила модуля авторизации.
```

## Выполнение команд

`task ready` проверяет полный Draft без изменения статуса. `task context`
собирает сведения начиная с Ready. `task verify --dry-run` возвращает план, а
`task verify --run` после локального gate последовательно выполняет выбранные
команды из корня репозитория.

Одинаковые команды выполняются один раз, даже если связаны с несколькими
targets. Ошибка одной команды не останавливает остальные. Команды считаются
доверенным кодом репозитория и выполняются с правами текущего пользователя.

Подробности форматов отчёта и exit codes находятся в
[CLI-контракте](../contracts/cli.md).
