# STD-DOCS-001: Проверяемая документация

Стандарт определяет, чему можно доверять при работе с документацией Toudocu.
Исходником служит Markdown в каноническом каталоге документации. Собранный
портал и другие производные файлы можно в любой момент пересоздать, поэтому
вручную их не редактируют. Исключение — распознанный OpenAPI-файл: он является
источником точного HTTP-контракта.

<!-- toudocu:section rules -->
## Правила

1. Общий продуктовый охват задаёт `roadmap.md`. Явно связанный сценарий `UC-*`
   завершён только при статусе группы `done`, хотя бы одной галочке в разделе
   «Критерии приёмки» и всех отмеченных галочках этого раздела. Чек-листы вне
   раздела не меняют готовность; `CON-*`, `CONTRACT-*`, `DLV-*` и
   `DELIVERABLE-*` сохраняют галочку дорожной карты.
2. Каталоги `build/`, `dist/` и `project-docs/` содержат локальный или
   созданный в CI результат. Их не хранят в Git и не редактируют как исходную
   документацию.
3. Публикуемый портал собирается из Markdown в CI после проверки структуры и
   смысла. Локальная сборка пишет результат только в игнорируемый или временный
   каталог.
4. Тип документа указывают, только когда его смысл действительно известен.
   Нельзя выдумывать дату, статус или процедуру лишь для того, чтобы
   убрать предупреждение.
5. Перед работой автор читает стандарты и эксплуатационные инструкции,
   указанные в контексте задачи. Для остальных стандартов он вручную проверяет
   поле `Область`: CLI намеренно не определяет применимость по шаблону пути.
6. Каталог `docs/runbooks/` создаётся только тогда, когда в проекте появилась
   реальная эксплуатационная инструкция `RB-*`.
7. `docs/architecture/overview.md` — обязательная карта архитектуры. Каждый
   другой Markdown-файл в `architecture/` отвечает на один конкретный вопрос
   и связан с обзором прямой ссылкой.
8. Подробные процессы, контракты, справочные факты, эксплуатационные
   инструкции, решения и модули остаются соответственно в документах
   `FLOW-*`, `CONTRACT`, `REFERENCE`, `RB-*`, `ADR-*` и `MOD-*`. Проверка
   архитектуры применяет к ним правила `ARCH001`–`ARCH013`.
9. `$toudocu refresh` обновляет всю исходную документацию, а
   `$toudocu refresh diff` — документацию, связанную с текущими изменениями
   Git. Оба режима опираются только на найденные в репозитории факты. Дата
   меняется вместе с содержанием или связями. Поле `Last verified` можно
   обновить лишь после реального выполнения описанной инструкции.
10. Если в корне репозитория есть `CHANGELOG.md`, только он считается журналом
    релизных изменений. Не нужно дублировать его в `docs/changelog.md` или
    создавать пустой корневой журнал ради вкладки портала.
11. Файлы `contracts/**/*.openapi.{yaml,yml,json}` определяют HTTP-пути,
    методы, параметры, заголовки, статусы, форматы данных, примеры и JSON-схемы.
    Сопроводительный Markdown объясняет поведение, безопасность, правила
    доступа к файлам и границы доверия, но не копирует схему. Внешние `$ref`
    не загружаются.

<!-- toudocu:section automated-checks -->
## Автоматические проверки

- `go run ./cmd/toudocu check ./docs --strict --stale-days 0` проверяет
  каноническую документацию в строгом режиме;
- тесты контролируют целостность шаблонов и публичной JSON-схемы;
- отдельные тесты проверяют ссылки, стабильные идентификаторы, контекст рабочих
  задач и навигацию портала.

Эти команды запускаются из рабочей задачи или доверенного CI, а не самим
стандартом.
