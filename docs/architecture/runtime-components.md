# Ответственность компонентов

Toudocu разделяет чистую модель, прикладные сценарии, внешние адаптеры, HTTP-сервер, CLI и
React-представление. Зависимости направлены внутрь: UI и адаптеры используют application/core, но
core не знает о React, HTTP и Node.js.

## Компоненты

| Часть                      | Ответственность                                                                  |
| -------------------------- | -------------------------------------------------------------------------------- |
| `packages/core`            | Markdown, модель проекта, связи, готовность задач и правила безопасности без I/O |
| `packages/application`     | Сценарии CLI, задач, сборки, изменений и Agent Console через явные порты         |
| `packages/contracts`       | Версионируемые DTO, runtime-схемы и реестр маршрутов                             |
| `packages/portal`          | Преобразование доменной модели в `PortalSnapshotV1` и `PageViewV1`               |
| `packages/platform-node`   | Файловая система, Git, процессы, PTY, skill и provider-адаптеры                  |
| `packages/server`          | Loopback HTTP/WebSocket API, watcher и жизненный цикл runtime                    |
| `apps/web`                 | Общие React-страницы статического портала и локального workspace                 |
| `apps/web/renderer`        | Предварительный рендер HTML рядом с общими React-страницами                      |
| `apps/cli`                 | Публичная командная строка и коды завершения                                     |
| `packages/integrations/bb` | Инструменты, workflow skill и панель bb через публичный CLI JSON                 |

CLI загружает проект через Node-адаптеры и вызывает application-сценарий. `build` передаёт готовую
модель renderer и атомарно публикует результат. `serve` хранит последний успешный снимок, а React
Router показывает его и локальные рабочие поверхности. Браузер не вычисляет доменные правила.

Плагин bb не импортирует core, application, platform-node или server. Он использует SDK bb для
выбора машины и workspace текущего thread, а контракты Toudocu — для проверки JSON. До создания
thread панель и mentions читают default checkout выбранного проекта; после создания — workspace
thread. Панель показывает дерево неархивированных задач и их текст из публичного `task list` JSON.
Снимок кратковременно кешируется отдельно для каждой машины и рабочей копии;
выбор задачи не запускает CLI. Git changes и план проверок запрашиваются только
при открытии соответствующей вкладки, а готовность перед запуском работы
повторно проверяется через CLI.
Связь thread с задачей хранится в состоянии плагина; доменная модель задачи остаётся в Toudocu.
Уточнение, ревью и явно выбранный запуск проверок создают отдельный thread в той же рабочей
копии, чтобы учитывать незакоммиченные изменения. Реализация стартует в управляемом worktree.
Действия запускают workflow навыка; `clarify` не выдаётся за команду CLI, а инструмент проверки
по-прежнему возвращает только план.
Плагин не запускает HTTP-сервер и не вычисляет готовность задач. Совместимость определяется через
[публичные команды discovery](../contracts/cli.md#обнаружение-проекта-и-возможностей).
Запущенный `serve` регистрирует экземпляр в пользовательском состоянии вне Git;
`project info` проверяет живой сервер для точной пары корней текущей рабочей копии.
Кнопка перехода в Toudocu использует этот адрес после проверки доступности с клиента,
а для удалённого loopback — защищённый канал bb Connect. Discovery ссылки обновляется
независимо от кеша задач и не требует сервера для обычной работы плагина.

Git diff, semantic diff, OpenAPI и данные задач анализируются независимо: ошибка дополнительного
представления не скрывает исходный патч. Обсуждения, Agent Session и Project Terminal существуют
только в основном loopback `serve`; статическая сборка их не включает.
