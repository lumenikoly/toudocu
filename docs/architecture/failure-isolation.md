# Изоляция ошибок документации и проверок

- Тип документа: Architecture
- Архитектурный вопрос: Как изолируются ошибки документации и запускаемых проверок?

Ошибки чтения и структуры превращаются в привязанные к документам diagnostics
и не открывают путь к исполнению. Явно запущенные проверки задачи выполняются
последовательно в отдельной границе процесса, а их сбои, timeout и ограниченный
вывод фиксируются в отчёте. Сам Docgent не переписывает исходный Markdown, но
разрешённые shell-команды имеют права текущего пользователя и могут менять
репозиторий.

## Область

Ответ описывает изоляцию двух классов отказов: недостоверной документации и
команд, разрешённых через task workflow. Сценарии пользователя остаются в
[FLOW-DOCS-CHECK](../flows/FLOW-DOCS-CHECK.md) и
[FLOW-TASK-WORKFLOW](../flows/FLOW-TASK-WORKFLOW.md).

## Ошибки документации

Сканирование продолжает собирать доступные документы, а validation добавляет
стабильные issues к общей модели и конкретным файлам. Наличие error делает
операцию неуспешной; warning меняет exit code только в strict mode. Ни один
диагностический путь не запускает команды work item.

## Ошибки запускаемых проверок

`task verify --run` сначала требует валидный task-local контракт. После допуска
каждая уникальная команда выполняется из repository root, и сбой одной команды
не скрывает результаты остальных. Timeout завершает дерево процессов, stdout и
stderr сохраняются ограниченным хвостом, а итоговый отчёт отделён от исходной
документации. Безопасность побочных эффектов самих команд обеспечивает доверие
к репозиторию и явное решение инициатора о запуске.
