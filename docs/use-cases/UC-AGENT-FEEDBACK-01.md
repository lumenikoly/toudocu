# UC-AGENT-FEEDBACK-01: Обсудить документацию с агентом разработки

- Идентификатор: UC-AGENT-FEEDBACK-01
- Статус: Готово
- Актор: Разработчик
- Модуль: MOD-AGENT-FEEDBACK
- Приоритет: Высокий
- Экраны: SC-SITE-DOCUMENT, SC-CHANGES-WORKSPACE
- Начальный экран: SC-SITE-DOCUMENT
- Конечные экраны: SC-SITE-DOCUMENT, SC-CHANGES-WORKSPACE
- Последнее обновление: 2026-08-12

Разработчик задаёт вопрос по актуальной документации или просит проверить и
изменить её, а агент разработки получает запрос через локальную команду и возвращает
ответ в исходное обсуждение.

## Предусловия

- канонический портал запущен через `toudocu serve` внутри Git-репозитория;
- агент разработки имеет установленный навык Toudocu и доступ к командам Toudocu;
- целевой файл Markdown находится в каноническом каталоге документации.

## Основной сценарий

1. Разработчик выделяет текст документа, включая заголовок, и открывает
   контекстное меню. Меню позволяет скопировать текст, скопировать контекст или
   добавить сообщение в обсуждение.
2. Разработчик выбирает тип `question` или `change_request`, вводит сообщение и
   сохраняет его. Сохранение атомарно создаёт ожидающую запись очереди, читает
   только целевой документ и локальное состояние и не строит Git-проекцию Changes.
3. Сообщение можно изменить или удалить, пока агент не получил его через
   `agent next`. После получения сообщение неизменяемо.
4. Панель обсуждений остаётся на текущей вкладке. Те же ветки видны в Портале и
   в «Изменениях»; переход между вкладками для ответа или закрытия не нужен.
5. Кнопка «Скопировать промт» немедленно копирует фразу «Обработай запросы из
   Toudocu.» и не меняет очередь.
6. Получив просьбу, агент разработки вызывает `toudocu agent next --json`, читает
   весь запрос и актуальный документ, затем получает необходимые
   доказательства из кода, тестов или конфигурации.
7. Для `question` агент возвращает объяснение без изменения документации. Для
   `change_request` он сначала проверяет факты, затем изменяет канонические
   документы либо объясняет, почему изменение не требуется.
8. Агент выполняет релевантные проверки и передаёт `AgentResponse` через
   `toudocu agent respond`. Ответ появляется в исходной ветке, которая остаётся
   открытой.
9. Разработчик закрывает обсуждение либо отправляет уточнение. Уточнение формирует
   новую запись очереди той же ветки.

## Альтернативные сценарии

- Если очередь пуста, `agent next --json` возвращает `pending=false` и код `0`.
- Если запись уже временно закреплена за обработчиком, второй обработчик получает
  `AGENT_INBOX_BUSY`. После истечения срока закрепления старейшая запись снова доступна.
- Если документ изменился, Toudocu переносит привязку при единственном точном
  совпадении текста либо единственной паре сохранённых контекстов. Иначе
  состояние становится `stale` или `deleted`.
- При состоянии `stale` агент перечитывает актуальный документ. Если намерение нельзя
  определить надёжно, он возвращает `needs_clarification`.
- Повторный идентичный ответ не создаёт второе сообщение. Другой ответ для той
  же завершённой записи даёт `AGENT_RESPONSE_CONFLICT`.
- Повреждённое локальное состояние не перезаписывается и возвращает
  `AGENT_STATE_CORRUPTED`.

## Постусловия

- разговор и очередь сохранены вне репозитория и переживают перезапуск;
- полученные агентом сообщения и ответы неизменяемы;
- файловая система и обычная пересборка являются источником фактических изменений;
- Toudocu не запускал языковую модель и не менял рабочий код.

## Критерии приёмки

- [x] Разговор и очередь сохранены вне репозитория и переживают перезапуск.
- [x] Ожидающие сообщения редактируемы, а полученные агентом сообщения и ответы
  неизменяемы.
- [x] Файловая система и обычная пересборка остаются источником фактических
  изменений.
- [x] Toudocu не запускает языковую модель и не меняет рабочий код.
